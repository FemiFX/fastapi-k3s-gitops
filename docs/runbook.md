# Runbook

## Purpose

This runbook contains the normal operating procedures for the application. It
is written for the person who has to start the stack, investigate a failed
deployment, check a backup, or recover the service without reconstructing the
commands from the repository.

The normal path is GitLab CI for deployments. The manual commands below are
for diagnosis, emergency recovery, and controlled demonstrations. Production
commands must be run against the production kubeconfig and namespace only
after the target has been checked.

## Before operating the system

Have the following available:

- access to the repository and the GitLab project;
- the appropriate kubeconfig for staging or production;
- SSH access through the Proxmox host when cluster access is not direct;
- the database and backup credentials when a restore is required;
- the restic repository password and read-only object-storage key for an
  off-site restore.

Never paste passwords into shell history or commit kubeconfig files, generated
.env files, or Kubernetes Secret manifests. The repository contains templates
and commands, not the secret values.

## Run the application locally

The local stack consists of the FastAPI container, PostgreSQL, and Traefik.
Start it from the repository root:

~~~sh
cp .env.example .env
docker compose up --build
~~~

The API is reached through the local Traefik entry point at
http://fastapi.localhost:8008. The Traefik dashboard is available at
http://fastapi.localhost:8081 and is exposed only on the local machine.

Useful checks:

~~~sh
curl http://fastapi.localhost:8008/health
curl http://fastapi.localhost:8008/ready
curl http://fastapi.localhost:8008/
docker compose ps
docker compose logs -f web
~~~

/health is independent of PostgreSQL and is suitable for liveness. /ready
checks the users table and returns HTTP 503 when the application cannot serve
its normal request. This difference is important during database startup and
failure recovery.

Stop the local stack with:

~~~sh
docker compose down
~~~

Use docker compose down -v only when intentionally deleting local database
data. That operation is destructive for the local volume.

## Inspect a remote cluster

The cluster kubeconfig files are generated by Ansible and are gitignored:

~~~sh
export KUBECONFIG=/path/to/kubeconfig-prod-server.yaml
kubectl get nodes
kubectl -n production get pods,svc,ingress
kubectl -n production get events --sort-by=.lastTimestamp
~~~

When the API server is reachable only through the Proxmox host, create an SSH
tunnel first:

~~~sh
ssh -L 6443:10.10.10.30:6443 <proxmox-ssh-user>@203.0.113.10
~~~

The kubeconfig must then point to the local end of the tunnel, or the command
must be run in the environment where the generated kubeconfig already has the
correct server address.

## Deploy a release

**The pipeline does not deploy. Argo CD does.**

A pipeline builds the image, scans it, then rewrites one line in an Argo CD
Application and pushes that commit. Argo CD, running inside the cluster, sees
git change and reconciles the cluster to match. The deploy is a consequence of
git changing, not of a job running.

The normal release process:

1. Merge into `main`. `release:staging` writes the new tag into
   `gitops/apps/staging/fastapi-app.yaml` and pushes.
2. `sync:staging` creates the Secrets, then **waits** until the image Argo CD
   is running is the image that was just requested, and runs a smoke test.
3. Verify staging.
4. Merge `main` into `production`. Same again for the production Application,
   with `release:production` behind a manual button.

Note what step 2 is for. Pushing a commit is a *request*; the job does not
finish until the cluster reflects it. Without that wait the pipeline would go
green on an intention.

### Secrets are the exception

Argo CD reconciles everything in `gitops/`. Secrets deliberately are not in
there, so `sync:*` creates them with `kubectl` from protected CI/CD variables:
`app-secrets` in the application namespace, `backup-offsite` in production, and
`alertmanager-mattermost` in `monitoring`.

The consequence, which matters on a freshly built cluster: **Argo CD will
create workloads that cannot start until a pipeline has run.** The symptom is
`CreateContainerConfigError` on every pod.

### Deploy a specific tag by hand

Edit the Application and push. There is no `helm upgrade` step:

~~~sh
python3 infra/ci/set-image-tag.py gitops/apps/staging/fastapi-app.yaml <tag>
git commit -am "Deploy <tag> to staging."
git push
~~~

### Watch it happen

~~~sh
ansible staging -m shell --become -a "k3s kubectl -n argocd get applications"
ansible staging -m shell --become -a "k3s kubectl -n staging get pods -o wide"
~~~

`Synced` means the cluster matches git. `Healthy` means the resources report
themselves ready. Neither means the application is correct -- that is what the
smoke test is for.

### Do not edit a running release

`selfHeal` is on. `kubectl edit`, `kubectl scale` and `helm upgrade` against a
reconciled namespace are all undone, usually within seconds, and the only trace
is a diff that briefly appeared and disappeared. To make a deliberate temporary
change, turn off auto-sync on that Application first.

## Inspect a failed deployment

Start with the workload status and recent events:

~~~sh
kubectl -n production get deployment,pods,svc,ingress
kubectl -n production describe deployment prod-fastapi-app
kubectl -n production get events --sort-by=.lastTimestamp | tail -30
~~~

Then inspect the application and database logs:

~~~sh
kubectl -n production get pods \
  -l app.kubernetes.io/name=fastapi-app,app.kubernetes.io/instance=prod \
  -o custom-columns=NAME:.metadata.name,COMPONENT:.metadata.labels.component
kubectl -n production logs pod/<application-pod> -c web
kubectl -n production logs statefulset/prod-fastapi-app-db --all-containers
kubectl -n production logs job/<job-name>
~~~

The chart uses the same release labels on the application and database Pods.
The database has component=db, while the application has no component label.
Use the exact application Pod name for logs; a broad Deployment or label query
can otherwise select the database Pod instead.

Common symptoms:

| Symptom | Likely area | What to check |
| --- | --- | --- |
| Pending Pod | storage, scheduling, or resources | PVC status, node capacity, and events |
| CrashLoopBackOff | application startup or configuration | previous container logs and Secret keys |
| readiness probe 503 | database connection or schema | DB logs, DB_HOST, and the users table |
| ingress returns 404 | hostname or Ingress rule | request Host header and rendered Helm values |
| certificate not ready | DNS, ACME, or Traefik | cert-manager resources, solver events, and DNS |
| no metrics in Prometheus | ServiceMonitor discovery | labels, namespace selector, and /metrics response |

The application image listens on port 8000. A probe aimed at port 80 or a
database probe that checks the wrong port will report a failure even when the
process itself is healthy.

## Restart a service safely

Prefer restarting only the affected workload:

~~~sh
kubectl -n production rollout restart deployment/prod-fastapi-app
kubectl -n production rollout status deployment/prod-fastapi-app --timeout=180s
~~~

`rollout restart` works under Argo CD, with a wrinkle worth knowing: it stamps
an annotation onto the pod template, Argo CD sees a diff from git, and
`selfHeal` removes it again -- which triggers a second rollout. The pods do
restart; they may restart twice. Harmless for the stateless tier, and a reason
not to use it casually on the database.

Do not restart PostgreSQL as a first diagnostic step. Inspect its logs,
readiness state, and volume first. The database is a StatefulSet with a
persistent volume, but a restart still interrupts requests.

For local development:

~~~sh
docker compose restart web
docker compose restart db
~~~

## Check persistence and backups

Check the database volume and scheduled backup resources:

~~~sh
kubectl -n production get statefulset,pvc,cronjob,jobs
kubectl -n production get pods -l app.kubernetes.io/component=backup
~~~

Run a backup immediately when investigating the backup path:

~~~sh
kubectl -n production create job \
  --from=cronjob/prod-fastapi-app-backup manual-$(Get-Date -Format yyyyMMddHHmmss)
kubectl -n production logs job/<job-name>
~~~

The backup job first writes a compressed PostgreSQL dump to a temporary
.partial file, verifies it, and renames it only after success. Production then
uploads the backup volume to Cloudflare R2 through restic. A successful
database dump and a successful off-site upload are both required for the job
to succeed.

The cluster backup credential cannot delete objects. Pruning is therefore a
separate, manual operation from a trusted machine with a privileged key. See
[data-management.md](data-management.md) for the retention and restore
procedure.

## Rebuild an environment from nothing

See [rebuild-staging.md](rebuild-staging.md).

Destroying staging and building it back is the only test that covers every
layer at once: the VM from Terraform, the OS and k3s from Ansible, the cluster's
contents from git, and the data from an off-site backup. It ends with a reboot
of the hypervisor, because configuration that applies is not the same as
configuration that persists, and only a power cycle tells the two apart.

## Restore a database

Restore only after confirming the namespace, target database, and dump file.
The restore command uses ON_ERROR_STOP=1 so that the job fails on the first
SQL error instead of appearing successful after a partial restore.

The chart's backup PVC is mounted into a temporary restore Job. The complete
template is documented in [data-management.md](data-management.md) and
[helm/README.md](../helm/README.md). In summary:

1. stop or isolate application traffic if the restore is being performed on
   production;
2. identify the exact dump to restore;
3. mount the backup PVC into a one-off Job;
4. decompress the dump into psql;
5. verify the restored row count and /ready;
6. remove the temporary Job after collecting its logs.

For an off-site recovery, restore the restic snapshot to a trusted machine
first, then load the recovered .sql.gz file into the target database. The
repository password is essential; losing it makes the encrypted repository
unrecoverable.

## Troubleshoot certificates and HTTPS

Inspect the Ingress and certificate resources:

~~~sh
kubectl -n production get ingress,certificate,certificaterequest,order,challenge
kubectl -n production describe certificate <certificate-name>
kubectl -n production logs deployment/cert-manager
kubectl -n traefik logs deployment/traefik
~~~

The most common ACME causes are:

- the public DNS record does not point to the production public address;
- port 80 is blocked, so the HTTP-01 challenge cannot be completed;
- the requested hostname differs from the Ingress hostname;
- the issuer or solver is in the wrong namespace;
- an old failed challenge is still being retried.

Do not repeatedly delete certificate resources as a first response. Capture
the resource descriptions and events first; the evidence is needed to
distinguish a DNS problem from a Traefik or cert-manager configuration problem.

## Roll back a release

**A rollback is a git revert.** Revert the commit that changed the image tag,
push, and Argo CD reconciles the cluster back.

~~~sh
git log --oneline -- gitops/apps/production/fastapi-app.yaml
git revert <the deploy commit>
git push
~~~

That is the whole procedure for production too: revert on the `production`
branch. It preserves the audit trail and leaves the cluster and git agreeing
with each other, which is the point of the whole arrangement.

**`helm rollback` no longer works here, and fails in a confusing way.** It will
appear to succeed, and `selfHeal` will put the release back within seconds,
because git still says what it said. Anything that edits the cluster directly
now loses an argument with a controller.

If a revert is not fast enough -- a live incident, and the previous tag is
known -- set the tag forward rather than reaching for `helm`:

~~~sh
python3 infra/ci/set-image-tag.py gitops/apps/production/fastapi-app.yaml <previous tag>
git commit -am "Roll production back to <previous tag>."
git push
~~~

Do not rewrite history on a protected branch for a normal incident.

## Respond to monitoring alerts

| Alert | First response |
| --- | --- |
| ApplicationNoReadyReplicas | inspect Pods, events, and /ready; check whether the DB or image is failing |
| ApplicationTargetDown | check Service endpoints, Pod readiness, and the ServiceMonitor |
| DatabaseDown | inspect the StatefulSet, PostgreSQL logs, PVC, and node storage |
| BackupJobFailed | inspect the latest Job logs and whether the backup PVC is writable |
| BackupStale | check CronJob scheduling, local time, and the latest verified dump |
| BackupMetricMissing | check whether the backup metric file is present and mounted |

### Where alerts go

| | Routed to | What arrives |
| --- | --- | --- |
| Production | Mattermost, plus Healthchecks.io for the Watchdog | Everything, grouped |
| Staging | A separate quiet Mattermost channel | **Critical only** |

Staging's channel is checked, not watched, and repeats every 12 hours rather
than every four. Warnings and the Watchdog stay inside the cluster. The point
of routing staging anywhere is that the path is real: a delivery path that has
never carried anything is indistinguishable from one that cannot.

**Do not delete a Job to clear `BackupJobFailed`.** It only looks at Jobs
created in the last 26 hours, so a single bad night clears itself. Deleting
objects to silence alerts is a habit worth never starting, particularly around
a backup system.

## Look at the dashboards

Grafana is ClusterIP only. It is never exposed to the internet -- an admin
console on a public address is a standing liability that buys nothing here --
so it is reached by forwarding a port through the jump host.

Two hops, in one terminal. SSH to the node, forwarding a local port, and start
the port-forward on the far end:

~~~sh
# staging: 10.10.10.20   production: 10.10.10.30
ssh -J <proxmox-ssh-user>@203.0.113.10 -L 3000:localhost:3000 femi@10.10.10.20
# then, on the node:
k3s kubectl -n monitoring port-forward svc/monitoring-grafana 3000:80
~~~

Then open <http://localhost:3000> in a browser on your own machine.

Get the password. Staging's lives in the `grafana-admin` Secret, which CI
creates from the `STAGING_GRAFANA_ADMIN_PASSWORD` variable; production's is set
by Ansible from `grafana_admin_password`. To read staging's back on the node:

~~~sh
k3s kubectl -n monitoring get secret grafana-admin   -o jsonpath="{.data.admin-password}" | base64 -d; echo
~~~

The user is `admin`.

**A rotated Secret does not change the login.** Grafana reads the password once,
when it first creates the admin account, and keeps it in its own database on
the PVC from then on. To really change it, change it inside Grafana:

~~~sh
k3s kubectl -n monitoring exec deploy/monitoring-grafana -c grafana --   grafana cli admin reset-admin-password <the new password>
~~~

### What is worth looking at

kube-prometheus-stack ships a large set of dashboards; these are the ones that
answer the questions this platform actually gets asked:

| Dashboard | Answers |
| --- | --- |
| **Kubernetes / Compute Resources / Namespace (Pods)** | Is anything about to be evicted on a 6 GB node |
| **Kubernetes / Compute Resources / Node (Pods)** | Where the memory went |
| **Node Exporter / Nodes** | Disk filling, which kills PostgreSQL first |
| **Alertmanager / Overview** | What is firing, and what is silenced |
| **Prometheus / Overview** | Whether Prometheus itself is keeping up |

To check a specific claim rather than browse, use Explore and a query:

~~~
kube_deployment_status_replicas_available{namespace="staging"}
ALERTS{alertstate="firing"}
~~~

`ALERTS` is a real time series, so it answers "was it firing last night", which
no `kubectl get` can.

### When a datasource does not appear

Grafana reads its provisioning files **once, at startup**. A datasource added to
the chart values reaches the cluster in three hops -- Argo CD updates a
ConfigMap, a sidecar container writes it into a shared volume, Grafana reads the
volume -- and only the first two happen on their own.

~~~sh
# Did the sidecar write it? The Grafana image has no shell; the sidecar does,
# and it mounts the same volume.
k3s kubectl -n monitoring exec deploy/monitoring-grafana -c grafana-sc-datasources --   cat /etc/grafana/provisioning/datasources/datasource.yaml

# In the file but not in the UI means Grafana has not re-read it
k3s kubectl -n monitoring rollout restart deploy/monitoring-grafana
~~~

Two quirks in that pod, both harmless and both confusing the first time:

- **No shell in the Grafana container.** `exec sh` fails with
  `executable file not found`. Debug from a sidecar, or use `kubectl cp`.
- **The sidecars log `OSError: [Errno 98] Address in use`** and fall back from
  watch mode to polling, because two of them want the same port. Files still
  get written; changes just take up to a minute rather than being instant.

### Logs

Loki stores the logs; Grafana queries it. Go to **Explore**, pick the **Loki**
datasource, and use LogQL.

A LogQL query is two halves: **a stream selector in braces, then filters.** The
selector picks which log streams by label; the filters grep inside them.

~~~
# Everything from the application
{namespace="staging", app="fastapi-app"}

# Errors only
{namespace="staging"} |= "ERROR"

# One pod, excluding the noise
{namespace="staging", pod="staging-fastapi-app-abc123"} != "GET /health"

# The database, last 15 minutes, around a restart
{namespace="staging", container="postgres"}

# How many errors per minute -- a metric derived from logs
sum(rate({namespace="staging"} |= "ERROR" [1m]))
~~~

The selector is not optional. `|= "ERROR"` on its own is not a query, because
Loki has no index of the words in your logs -- only of the labels. That is the
whole design, and it is why it runs on this node at all.

**Labels are namespace, pod, container and app.** Nothing else. A label with
many possible values -- a request id, a user id -- would create a separate
stream per value and bring Loki down.

### Prove logs are actually arriving

A log collector that collects nothing looks exactly like a quiet system. Alloy
runs, reports healthy, and ships zero lines if it cannot see the files. So ask
Loki what it has, rather than trusting that the pods are up:

~~~sh
# Which streams exist at all. An empty list means nothing is being collected.
ansible staging -m shell --become -a "cmd='k3s kubectl -n monitoring run lokicheck --rm -i --restart=Never --quiet --image=curlimages/curl:8.10.1 -- -s http://loki:3100/loki/api/v1/labels'"

# Which namespaces have logs
ansible staging -m shell --become -a "cmd='k3s kubectl -n monitoring run lokicheck --rm -i --restart=Never --quiet --image=curlimages/curl:8.10.1 -- -s http://loki:3100/loki/api/v1/label/namespace/values'"
~~~

`{"status":"success","data":[]}` means Alloy is not delivering. Check its logs
and whether `/var/log` is mounted into the pod:

~~~sh
ansible staging -m shell --become -a "cmd='k3s kubectl -n monitoring logs -l app.kubernetes.io/name=alloy --tail=50'"
ansible staging -m shell --become -a "cmd='k3s kubectl -n monitoring get ds alloy -o jsonpath={.spec.template.spec.volumes}'"
~~~

This is the same habit as asking Prometheus whether the target is up instead of
trusting that `kubectl apply` succeeded. **A pipeline that reports healthy and
moves no data is the failure mode worth designing a check around.**

### Why this beats `kubectl logs`

| | `kubectl logs` | Loki |
| --- | --- | --- |
| A pod that has been replaced | gone | 7 days |
| Across several pods at once | one at a time | one query |
| A backup Job that ran at 3am and exited | gone with the pod | still there |
| Correlated with a CPU spike | by eye, in two windows | same timeline |

`kubectl logs` is still the right tool for what a container is printing *right
now*. Loki is for what something printed *then*.

### What still has no logs here

- **Anything before Alloy was installed.** Collection starts when the collector
  does.
- **Why a pod will not start.** `CreateContainerConfigError` and
  `ImagePullBackOff` produce no logs at all, because no container ever ran.
  That is `kubectl describe pod`, and it always will be.
- **k3s itself.** `journalctl -u k3s` on the node. The node's own services are
  outside the cluster's log collection.
- **Production.** Staging only, for now.

## Evidence to record

Record the environment, commit or Helm revision, UTC timestamps, commands that
were run, relevant logs, resulting health responses, and whether data was
restored. This turns an ad-hoc recovery into evidence that can be reviewed and
repeated.
