# Application and API

## Purpose

The application is a deliberately small FastAPI service. It provides enough
behavior to demonstrate container packaging, database persistence, health
checks, metrics, testing, and deployment. It is not intended to be a complete
user-management system.

## Application structure

| File | Responsibility |
| --- | --- |
| app/config.py | Loads DATABASE_URL from the environment |
| app/db.py | Defines the Ormar model, async database configuration, schema creation, and schema check |
| app/main.py | Creates the FastAPI application, lifespan, endpoints, metrics, and readiness logging |
| tests/conftest.py | Provides a TestClient whose lifespan connects to PostgreSQL |
| tests/test_health.py | Verifies liveness and readiness behavior |
| tests/test_metrics.py | Verifies Prometheus metrics and probe exclusion |
| tests/test_users.py | Verifies the user response and seed record |

## Data model

The database contains a users table represented by the User model:

| Field | Type | Rules |
| --- | --- | --- |
| id | integer | Primary key |
| email | string | Required, unique, maximum 128 characters |
| active | boolean | Required, defaults to true |

The application currently exposes only a read operation for this model. During
startup it creates the example user test@test.com if that user does not
already exist. There is no public endpoint for creating, changing, or deleting
users.

## Database lifecycle

The application uses an asynchronous SQLAlchemy engine through Ormar. The
database URL is accepted in its normal PostgreSQL form, for example:

~~~text
postgresql://user:password@db:5432/database
~~~

app/db.py changes this to an asyncpg URL internally. This keeps Compose,
Helm, CI, and local tooling consistent while ensuring the application uses the
async driver.

The FastAPI lifespan runs before the first request:

1. Open the database connection.
2. Create missing tables with SQLAlchemy metadata.
3. Create the example user if necessary.
4. Serve requests.
5. Close the connection during shutdown.

Schema creation is currently handled at startup. There is no Alembic or other
migration system. This is acceptable for the small training application, but
it would not be a sufficient schema-change process for a larger production
service. A migration tool should be introduced before incompatible schema
changes are made.

## API endpoints

### GET /

Returns all rows from users. A normal response is a JSON array containing
objects with id, email, and active fields.

The endpoint depends on PostgreSQL. If the database or table is unavailable,
the request fails and the readiness endpoint should also report failure.

### GET /health

Returns:

~~~json
{"status": "ok"}
~~~

This is the liveness endpoint. It does not access PostgreSQL. Its purpose is to
show that the process and event loop are responsive. Kubernetes uses it for the
liveness and startup probes.

### GET /ready

Returns:

~~~json
{"status": "ready"}
~~~

The endpoint queries the users model. This checks both that PostgreSQL is
reachable and that the table the application serves exists and is queryable.

If the check raises an exception, the endpoint returns HTTP 503:

~~~json
{"detail": "database not ready"}
~~~

The original exception is logged. The response intentionally contains a short
stable message instead of database internals.

### GET /metrics

Returns Prometheus text-format metrics generated by
prometheus-fastapi-instrumentator. Request counts, durations, and response
sizes are collected for application traffic. /health, /ready, and /metrics
itself are excluded so probe traffic does not dominate the useful
measurements.

The endpoint is not included in the generated OpenAPI schema. In the current
Ingress configuration it is still reachable through the application route, so
whether it should be restricted is a security decision for a future hardening
pass.

## Why liveness and readiness are separate

A liveness failure tells Kubernetes to restart a container. A readiness failure
removes the Pod from the Service without restarting it. A temporary database
outage should normally stop traffic to the Pod, not restart every healthy
application process. That is why /health is dependency-free and /ready
checks the database.
